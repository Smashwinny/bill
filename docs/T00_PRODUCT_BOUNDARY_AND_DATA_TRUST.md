# T00 产品边界与数据可信度规范（修订版）

本文仅作为 T00 代码规范与验收依据，不可用于证明功能已完成。后续代码实现必须以本规范为准。

## 1. 数据来源边界

### 1.1 支持来源
1. 通知事件
- 来源：系统通知（含通知标题、正文、时间戳、关键元数据）
- 价值：用于形成候选交易事件、触发人工核验；不能直接作为最终财务真值。

2. 用户人工证据
- 来源：用户主动补充的确认/纠正/备注信息
- 价值：作为独立证据链参与状态推进与异常处理，但仍需与权威账单或渠道账单形成一致性。

3. 官方账单或官方渠道 API（需通过身份/覆盖期/完整性校验）
- 来源：用户可导出的官方账单、渠道侧可验证 API 接口返回
- 价值：作为最终真值（Authority Source）用于确认、对账和覆盖。

### 1.2 不支持来源（严格禁止）
1. 读取其他 App 私有数据库
- 不进行进程间数据库访问、内容提供器越权读取或任何形式的持久数据抓取。

2. 辅助功能抓屏 / UI 自动化
- 不使用 Accessibility 抓屏、无障碍自动交互、OCR 识别页面元素替代官方数据。

3. 网络抓包
- 不通过抓包、MITM 或协议监听获取支付内容。

4. 短信
- 短信默认不纳入首版支持范围。
- 仅在未来渠道接入前，需按渠道逐一完成验证再决定是否放开。

## 2. 交易状态定义与状态机（金额与证据规则）

定义以下 5 个交易状态，并为每个状态明确：
- 进入条件
- 退出条件
- 证据不足时处理

### 2.1 DETECTED（检测到）
- 进入
  - 至少有一条来源为“通知事件”的候选命中，但证据不足以确认支付成功/失败/金额/渠道真实性。
- 退出
  - 符合 SUCCESS、REVERSED 或可关联的退款事件（2.3）后迁移。
- 证据不足
  - 保持 DETECTED。
  - 暂不入账，不更新净额；显示“待人工核验”。

### 2.2 SUCCESS（成功）
- 进入
  - 符合以下条件任一项：
    - 官方账单/官方渠道 API 在“来源身份 + 覆盖期 + 完整性”三项校验通过时声明成功；
    - T04 真机验证通过、来源包与解析版本已匹配，且通知语义明确为“成功”，并且金额、商户、时间完整且无冲突。
  - 不再要求人工证据作为进入条件；人工确认仅作为独立可审计证据。
- 退出
  - 出现 REVERSED、PARTIALLY_REFUNDED、FULLY_REFUNDED 的权威证据。
- 证据不足
  - 若金额、商户、时间存在关键缺失，转入 DETECTED 而非 SUCCESS。

### 2.3 REFUNDED（退款事件，非交易状态）
- 定义
  - 退款是独立财务逆向事件，不是交易状态；仅在与先前已确认 SUCCESS 的原交易建立可核验关系后才生效。
  - 退款记录可有多条，需通过可追溯字段（如 `originalTransactionId`）进行链路关联，支持累计。
- 进入
  - 有可追溯来源（通知/官方账单/官方渠道 API）的退款记录，并与 SUCCESS 原交易建立可核验关联。
  - 可按时间窗口与金额进行幂等防重。
- 退出
  - 退款记录通过累计规则更新原交易状态（PARTIALLY_REFUNDED/FULLY_REFUNDED）。
- 证据不足
  - 无法关联原交易时，不进入交易状态机，不作为 REVERSED 处理；进入待确认异常。

### 2.4 PARTIALLY_REFUNDED（部分退款）
- 进入
  - 与 REFUNDED 关联且 `cumulative_refund < original_paid_amount`。
  - `0 < cumulative_refund < original_paid_amount`。
  - 需具备退款来源可追溯（通知/官方账单/渠道 API）与交易匹配关系。
- 退出
  - 如果累计退款增长到等于原始支付金额 => FULLY_REFUNDED。
  - 若出现权威来源明确否定支付成立或独立可核验冲正/撤销/回滚链路，迁移到 REVERSED。
- 证据不足
  - 退款无法可靠关联到原交易时进入异常队列，不能自动归入 PARTIALLY_REFUNDED。

### 2.5 FULLY_REFUNDED（全额退款）
- 进入
  - 存在与原交易关联的退款事件累计达到原始金额：`cumulative_refund == original_paid_amount`。
- 退出
  - 若后续出现再次退款造成累计超额（超出原金额）=> 异常；不得静默覆盖旧金额。
- 证据不足
  - 无法确认原始金额边界时，不得标记 FULLY_REFUNDED；保留可审计异常状态待处理。

### 2.6 REVERSED（撤销/冲正）
- 进入
  - 仅当同一交易先有 SUCCESS，并且官方/可核验渠道明确发布“冲正/撤销/回滚”语义，明确否定该交易成立关系时，才进入 REVERSED。
  - 该动作不创建退款收入，也不依赖退款记录推断；仅在渠道权威语义成立时入 REVERSED。
  - 与“初始未成功/账单覆盖期内完全不存在该交易/通知模糊”场景区分：此类场景不得入 REVERSED，只能进入“无效尝试”或“待确认”。
- 退出
  - 与同一交易存在新权威证据冲突并能说明更正时，进入异常审核或重新判定。
- 证据不足
  - 无法确认原交易成功结算时，禁止直接入 REVERSED；保留待确认。

### 2.7 异常金额规则
- 若 `cumulative_refund > original_paid_amount`，进入异常队列（不可自动确认）。
- 超额应保留完整审计证据，不得自动修正。
- 必要时允许用户标记“数据噪声/重复触发”，但不改变金额真值。

### 2.8 成功结算与撤销/冲正、退款事件的严格区分
- 成功结算后的退款链路：先确认该笔交易已入 SUCCESS，再按累计规则处理部分/全额退款更新。
- 原交易被权威证据否定（例如账单不认定、渠道 API 显示失败/取消）：标记为不可计入财务结算，不得作为 REVERSED 后续动作，应转入“无效尝试/待确认”复核。
- 仅基于通知“像样式像已付款”不构成结算完成依据。

## 3. 可信度分层（人工确认与对账）

### 3.1 待确认（Pending Verification）
- 定义：置信度状态，不是交易状态，不替代 2.x 状态机状态。
- 触发：核心证据存在冲突、字段缺失、重放冲突、来源身份/覆盖期/完整性校验失败。
- 证据冲突时将状态保持不变，可信度降为待确认并冻结自动状态迁移，直到新证据消解冲突。
- 条件：未能通过成功结算或退款的核心证据链。
- 行为：可见但不入正式财务统计。

### 3.2 自动确认（Auto Verified）
- 条件：满足解析规则并通过稳定规则、去重、来源身份/版本控制与幂等校验，且无冲突证据。
- 限制：非最终态，不得作为“已对账”。
- 必须在列表中清晰标注。

### 3.3 已对账（Reconciled）
- 条件：至少有一条权威账单/官方渠道 API 记录完成身份、覆盖期、完整性三项检查匹配。
- 覆盖：仅在以上三项全部通过后方可覆盖状态；覆盖前后必须保留原始状态快照与决策原因。
- 注：未完成匹配前，任何状态都不允许显示为已对账。

### 3.4 用户手工确认作为独立来源
- 用户确认是独立证据来源，不与权威账单等价。
- 用户确认必须落入审计日志（操作时间、对象、理由、操作者）。
- 不允许“用户确认即视为对账通过”。

## 4. 冲突策略（通知与账单冲突）

- 通知与账单发生冲突时不得静默覆盖。
- 冲突处理原则：
  1. 先保持当前状态，不自动回滚。
  2. 进入待审计的冲突状态。
  3. 仅当“账单来源身份 + 覆盖期 + 完整性”三项都通过后，才可覆盖候选状态为权威值。
  4. 覆盖前后必须保留原始状态快照与冲突决策原因，供审计追踪。
  5. 覆盖期间交易状态不替换为待确认，状态保持不变，可信度可降为待确认并冻结自动变更。

## 5. 本地存储与日志规则

- 1) 普通日志/诊断导出（含 Logcat、诊断导出、测试夹具、Git）：禁止写入原始通知正文、完整订单号、身份敏感字段（姓名、电话、身份证、卡号、支付 token、定位等）及可逆脱敏前数据。
- 2) 加密备份：仅在用户明确授权与隐私影响评估后启用，默认不含原始通知正文；可同步用于完成迁移所需的账目字段（金额、商户、交易时间、交易状态、退款累计、退款关系链）。
- 3) 传输与存储都必须按最小化字段原则处理，不得为方便调试放宽隐私底线。
- 保留/删除策略
  - 本阶段不定义最终保留时长与清理策略。
  - 后续任务单独补充到数据治理文档。

## 6. 同步策略（未来方向）

- 未来允许端到端加密同步以下内容（均在独立授权与评估通过后）：
  - 完整账目
  - 退款关系链
  - 审计元数据（创建/修改/覆盖决策）
- 原始通知正文默认不同步，普通同步不含原始正文。
- 如需同步原始通知正文，必须经过新版本用户授权与隐私影响评估后方可启用。

## 7. 风险边界

- 仅依赖通知不能承诺“零漏记、零多记”。
- 系统应显式提示：通知仅是高频入口信号，真正财务真值取决于后续核验与对账。

## 8. T00 十项人工验收问题（明确答案）

1. 收到支付提醒是否一定创建正式账目？
- 不一定。收到提醒可进入 `DETECTED` 或待确认场景；进入正式账目需满足 SUCCESS 条件并通过可信度路径（自动确认或人工复核放行）。

2. 没有支付提醒是否可以证明没交易？
- 不能。未收到提醒仅代表采集通道未捕获该事件，不等于交易不存在；需以官方账单/渠道对账确认。

3. 什么证据可判定“成功”？
- 符合以下任一：
  - 权威账单/官方渠道 API 的成功记录（需完成身份、覆盖期、完整性校验）；
  - T04 真机验证通过后，来源包匹配且解析版本受控、语义明确为“成功”、金额完整、无冲突。

4. 微信和银行双通知如何去重？
- 仅在存在可共享的稳定订单标识时可直接确认并合并；微信与银行通常订单标识不同，不以单一金额或短时间窗口判定同一交易。
- 当共享标识不可得时，仅使用金额、商户、时间窗、文本规范化形成“重复候选”；证据不足不得自动合并，需进入待确认。
- 不能将“相同金额短时间连续消费”直接合并为同一交易，必须有可核验交易关系后才合并。

5. 退款找不到原支付怎么办？
- 记录为退款待确认异常，不进入 REVERSED，不误计为收入，不自动关闭原交易；保留原始证据等待人工关联或补齐来源。

6. 部分/多次退款怎么算？
- 按累计退款额 `cumulative_refund` 计算：
  - `0 < cumulative_refund < original_paid_amount` 为 PARTIALLY_REFUNDED。
  - `cumulative_refund == original_paid_amount` 为 FULLY_REFUNDED。
  - 超过原金额进入异常，禁止自动确认。

7. 通知与账单冲突谁优先？
- 冲突时不静默覆盖；先冻结自动变更并将可信度降待确认，待账单来源身份、覆盖期、完整性校验通过并保留冲突审计后再覆盖。

8. 如何知道采集失效？
- 看采集健康面板：通知权限、监听服务状态、最近事件时间、目标包通知白名单状态、无事件告警阈值、系统报错与重启记录。

9. 哪些隐私信息禁止日志/Git/普通诊断导出？
- 普通日志、诊断导出、测试夹具与 Git 禁止写入：完整通知正文、完整订单号、完整姓名/电话、身份证/卡号、支付 token、定位、原始截图原文等。
- 加密备份在授权后可含最小必要账目字段，但默认不包含原始通知正文；如需扩展，需新建独立授权条款并更新最小字段清单。

10. 是否承诺通知零漏零重？
- 不承诺零漏/零重；只能承诺“可检测、可审计、可对账”，并持续通过账单与人工反馈纠偏。

## 9. 术语自检与一致性要求

- `DETECTED`、`SUCCESS`、`PARTIALLY_REFUNDED`、`FULLY_REFUNDED`、`REVERSED` 为交易状态。
- `待确认`、`自动确认`、`已对账` 为可信度/对账层。
- `REFUNDED` 作为退款事件实体定义（需 `originalTransactionId`）；不得与 `REVERSED` 混用。
- 当出现状态与可信度冲突时，状态不变、可信度降待确认并冻结自动变更。
