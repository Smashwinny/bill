# T00 产品边界与数据可信度规范（草案）

本文仅作为 T00 代码规范与验收依据，不可用于证明功能已完成。仅新增本文件，后续代码实现必须以本规范为准。

## 1. 数据来源边界

### 1.1 支持来源
1. 通知事件
- 来源：系统通知（含通知标题、正文、时间戳、关键元数据）
- 价值：用于形成候选交易事件、触发人工核验；不能直接作为最终财务真值。

2. 用户人工证据
- 来源：用户主动补充的确认/纠正/备注信息
- 价值：作为独立证据链参与状态推进与异常处理，但仍需与权威账单或渠道账单形成一致性。

3. 官方账单或官方渠道 API（需通过身份/覆盖期/完整性校验）
- 来源：用户可导出的官方账单、渠道侧可验证 API 接口返回
- 价值：作为最终真值（Authority Source）用于确认、冲正和对账。

### 1.2 不支持来源（严格禁止）
1. 读取其他 App 私有数据库
- 不进行进程间数据库访问、内容提供器越权读取或任何形式的持久数据抓取。

2. 辅助功能抓屏 / UI 自动化
- 不使用 Accessibility 抓屏、无障碍自动交互、OCR 识别页面元素替代官方数据。

3. 网络抓包
- 不通过抓包、MITM 或协议监听获取支付内容。

4. 短信
- 短信默认不纳入首版支持范围。
- 仅在未来渠道接入前，需按渠道逐一完成验证再决定是否放开。

## 2. 交易状态定义与状态机（金额与证据规则）

定义以下 5 个状态，并为每个状态明确：
- 进入条件
- 退出条件
- 证据不足时处理

### 2.1 DETECTED（检测到）
- 进入
  - 至少有一条来源为“通知事件”的候选命中，但证据不足以确认支付成功/失败/金额/渠道真实性。
- 退出
  - 符合 SUCCESS、REVERSED 或（若可关联）退款链路的证据时迁移。
- 证据不足
  - 保持 DETECTED。
  - 暂不入账，不更新净额；显示“待人工核验”。

### 2.2 SUCCESS（成功）
- 进入
  - 通知事件与人工证据、或官方账单（必须优先）共同支持“支付成功”。
  - 若仅有单一低置信度通知事件，不得直接进入 SUCCESS。
- 退出
  - 出现 REVERSED、PARTIALLY_REFUNDED、FULLY_REFUNDED 的权威证据。
- 证据不足
  - 若金额、商户、时间存在关键缺失，转入 DETECTED 而非 SUCCESS。

### 2.3 PARTIALLY_REFUNDED（部分退款）
- 进入
  - 有退款事件与对应交易归属关系。
  - 计算 `cumulative_refund`：
    - `0 < cumulative_refund < original_paid_amount`。
  - 需具备退款来源可追溯（通知/官方账单/渠道 API）与交易匹配关系。
- 退出
  - 如果累计退款增长到等于原始支付金额 => FULLY_REFUNDED。
  - 若出现权威来源否定支付成立或撤单/冲正链路，迁移到 REVERSED。
- 证据不足
  - 退款无法可靠关联到原交易时进入异常队列，不能自动归入 PARTIALLY_REFUNDED。

### 2.4 FULLY_REFUNDED（全额退款）
- 进入
  - 存在退款事件，且 `cumulative_refund == original_paid_amount`。
  - 或原交易原始成功状态被已核验的权威账单声明“已全额冲正”。
- 退出
  - 若后续出现再次退款造成累计超额（超出原金额）=> 异常；不得静默覆盖旧金额。
- 证据不足
  - 无法确认原始金额边界时，不得标记 FULLY_REFUNDED；保留可审计异常状态待处理。

### 2.5 REVERSED（撤销/冲正）
- 进入
  - 成功结算后的退款/撤销：只有在检测到“原交易成功结算”之后，出现官方/可核验渠道的反向账务动作。
  - 与“初始未成功”场景区分：若原交易未形成有效成功结算，需追踪为“无效尝试/待确认”，不默认入 REVERSED。
- 退出
  - 与同一笔交易存在新权威证据冲突并能说明更正时，进入异常审核或重新判定。
- 证据不足
  - 无法确认原交易成功结算时，禁止直接入 REVERSED；保留待确认。

### 2.6 异常金额规则
- 若 `cumulative_refund > original_paid_amount`，进入异常队列（不可自动确认）。
- 超额应保留完整审计证据，不得自动修正。
- 必要时允许用户标记“数据噪声/重复触发”，但不改变金额真值。

### 2.7 成功结算与撤销/冲正的严格区分
- 成功结算后的退款：先确认该笔交易已完成结算，再确认其退款。
- 原交易被权威证据否定（例如账单不认定、渠道 API 显示失败/取消）：标记为不可计入财务结算，不能当作 REVERSED 的后续动作。
- 仅基于通知“像样式像已付款”不构成结算完成依据。

## 3. 可信度分层（人工确认与对账）

### 3.1 待确认（Pending Verification）
- 条件：未能通过成功结算或退款的核心证据链。
- 行为：可见但不入正式财务统计。

### 3.2 自动确认（Auto Verified）
- 条件：满足解析规则并通过重复校验（如幂等关联）但未匹配权威账单。
- 限制：非最终态，不得作为“已对账”。
- 必须在列表中清晰标注。

### 3.3 已对账（Reconciled）
- 条件：至少有一条权威账单/官方渠道 API 记录完成身份、覆盖期、完整性三项检查匹配。
- 注：未完成匹配前，任何状态都不允许显示为已对账。

### 3.4 用户手工确认作为独立来源
- 用户确认事件是独立证据来源，不与权威账单等价。
- 用户确认必须落入审计日志（操作时间、对象、理由、操作者）。
- 不允许“用户确认即视为对账通过”。

## 4. 冲突策略（通知与账单冲突）

- 通知与账单发生冲突时不得静默覆盖。
- 冲突处理原则：
  1. 先保持当前状态，不自动回滚。
  2. 进入待审计的冲突状态。
  3. 仅当“账单来源身份 + 覆盖期 + 完整性”三项都通过后，才可覆盖候选状态为权威值。
- 覆盖前后必须保留原始状态快照与冲突决策原因，供审计追踪。

## 5. 本地存储与日志规则

- 允许加密保存原始通知正文，用于追溯、回放与规则复测。
- 禁止写入：
  - Logcat 可见的完整通知正文
  - 测试夹具中的敏感内容
  - Git 仓库
  - 普通诊断导出文件
- 保留/删除策略
  - 本阶段不定义最终保留时长与清理策略。
  - 后续任务单独补充到数据治理文档。

## 6. 同步策略（未来方向）

- 未来允许端到端加密同步以下内容：
  - 完整账目
  - 退款关系链
  - 审计元数据（创建/修改/覆盖决策）
- 原始通知正文默认不同步。
- 如需同步原始正文，必须经过新版本用户授权与隐私影响评估后方可启用。

## 7. 风险边界

- 仅依赖通知不能承诺“零漏记、零重记”。
- 系统应显式提示：通知仅是高频入口信号，真正财务真值取决于后续核验与对账。

## 8. T00 十项人工验收问题（明确答案）

1. 该项目是否应按“通知优先”还是“账单优先”处理？
- 答：不是单一优先级策略。以通知作为入口，账单作为权威真值；冲突时保留审计，账单通过身份/覆盖期/完整性后才可覆盖。

2. 是否将短信作为首版数据来源？
- 答：否。首版默认不支持，需按渠道单独验证后再纳入。

3. 是否允许读取其他 App 私有数据库？
- 答：不允许，严格禁止。

4. 部分退款状态判定阈值是多少？
- 答：`0 < cumulative_refund < original_paid_amount`。

5. 何时进入 FULLY_REFUNDED？
- 答：当 `cumulative_refund == original_paid_amount`，且退款归因可核验。

6. 累计退款超过原金额怎么办？
- 答：进入异常，不自动确认，保留审计并阻断状态自动推进。

7. 用户手工确认能否替代账单对账？
- 答：不能。用户确认是独立证据，必须写入审计；未匹配权威账单前不标“已对账”。

8. 通知和账单冲突时是否可静默覆盖？
- 答：不可以。必须保留原状态与冲突审计，经过校验后才覆盖。

9. 原始通知正文能否全部同步到云？
- 答：默认不能。默认不同步，仅在未来获得明确授权后按最小必要范围启用。

10. 该系统是否可承诺“零漏记/零重记”？
- 答：不能。必须在界面和文案中声明无法承诺；需持续靠人工核验与对账约束误差。
