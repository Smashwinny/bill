# V1.1 实时采集与防漏防重实施方案（修订基线）

状态：已确定，作为实时采集层的开发基线
与既有文档的关系：

- 本文是对 `V1_PERSONAL_COMPLETE_LEDGER_ARCHITECTURE.md`（下称 V1）的修订与补充。V1 的第 1、2、3、5、6、7、8、11 章继续有效；与本文冲突处以本文为准。
- 本文取代 `T00_PRODUCT_BOUNDARY_AND_DATA_TRUST.md` §1.2 中"短信不纳入""禁止辅助功能"两条禁令，取代范围仅限本文第 3 章规定的受限用法。T00 的状态机、可信度分层、冲突策略与隐私条款继续有效。

## 1. 目标与承诺边界

需求原文："实时抓到用户付款并记录下来，不可以漏记，不可以记重复。"

本方案对该需求做如下工程化分解，任何实现与验收不得偏离：

| 层 | 交付物 | 时效承诺 | 正确性承诺 |
|---|---|---|---|
| 实时采集层 | Observation（原始观察）+ 候选交易 | 支付发生后秒级产生候选 | 不漏：见 §4 崩溃安全与补偿机制；不重：允许冗余候选，不产生正式账 |
| 对账层 | CanonicalTransaction / LedgerEntry（正式账） | 权威流水可取得后（渠道账单 T+0~T+1，银行 T+1） | 零漏记、零重复、零未解释差额（V1 §11 验收表达式） |

明确不承认的承诺：实时层单独承诺"零漏零重"。理由：实时层所有来源（通知、短信、页面）都是观察证据，渠道可以不发、系统可以不投递、服务可以被杀。零漏零重只能由权威流水对账闭合。实时层的职责是把"漏"的概率压到最低、把"漏没漏"变得可检测。

## 2. 权限清单（不使用 Root/Hook）

本方案需要的全部权限与系统设置如下，共六项授权 + 三项保活设置，均在用户手机上一次性引导完成：

1. 通知使用权（`BIND_NOTIFICATION_LISTENER_SERVICE`，系统设置页授权）。
2. 短信权限：`READ_SMS` + `RECEIVE_SMS` 运行时权限。**取代 V1 §4.2 的"默认短信应用"方案**，理由见 §3.2。
3. 无障碍服务（受限观察器，见 §3.3）。
4. 悬浮窗权限（仅用于 Debug 构建的采集状态指示，正式运行非必需）。
5. 自启动权限（HyperOS 设置页手动开启）。
6. 后台弹出界面权限（HyperOS 特有，供兜底提醒使用）。
7. 电池优化：设为"无限制"。
8. 省电策略：设为"无限制"（HyperOS 应用省电策略页）。
9. 锁屏清理：加入清理白名单。

**不使用 Root/Hook/Shizuku 读金融 App 数据**，理由（此决定不可在后续任务中自行推翻）：

- Root/Hook 读到的是与通知同源的非权威数据，对"零漏零重"这一完整性结论零增量——完整性由权威流水对账闭合，不由采集深度闭合。
- Root 会触发支付宝/微信/银行 App 的 Play Integrity 与环境检测，导致功能受限或封号，直接摧毁本方案赖以兜底的权威来源，并污染唯一目标设备的可信状态。
- ADB 仅保留用于开发调试、权限核验与健康检查（V1 §4.5 不变）。

## 3. 采集通道

### 3.1 通知监听（主通道）

在 V1 §4.1 基础上，以下为实现级强制要求：

1. **回调内同步落盘**。`onNotificationPosted` 中直接完成原始事件的 append-only 同步写入（单条 Room 插入，开启 WAL）。解析、分类、匹配全部异步。禁止在回调里 `launch` 协程后再写库——进程在协程执行前被杀即永久丢失且无迹可查（现行 T04 探针存在此缺陷，M1 必须重写该路径）。
2. **重连补偿扫描**。`onListenerConnected` 后调用 `getActiveNotifications()` 做全量扫描，与库内 `(package, user, key)` 比对，补录断连期间仍存活在通知栏的事件，标记来源为 `RECONNECT_SWEEP`。这是通知层抗漏记的核心保险。
3. **通知移除事件**。`onNotificationRemoved` 只记录元数据（key、移除原因），不删除已存观察。
4. **多用户与双开**。以 `sbn.getUser()` 区分 UserHandle 存储；HyperOS 应用双开产生同包名不同 user 的通知。账户登记流程必须询问用户是否存在双开支付/银行应用，未声明的双开实例产生的观察单独成组，不与主空间配对。
5. **双时间戳**。每条观察同时存 `postTime`（事件时间，对账与排序一律以它为准）与本地接收时间。
6. **通知 key 修订链**。同 key 不同内容哈希：存新 `ObservationRevision`（V1 §5.4 不变）；同 key 同哈希：记重复投递计数，不产生新行。

### 3.2 短信（银行通道）

**修订 V1 §4.2**：不申请默认短信角色。本项目为自用侧载、不上架，直接申请 `READ_SMS` + `RECEIVE_SMS` 运行时权限即可：

- `RECEIVE_SMS` 使本应用通过 `SMS_RECEIVED` 广播实时收到新短信（该广播投递给所有持权应用，不限默认短信应用）；Play 商店对该权限的声明限制仅约束上架分发，与侧载无关。
- `READ_SMS` 用于首次启用时回填历史银行短信、以及补偿广播丢失后的差量拉取（按 `date > 游标` 查询 SMS Provider）。
- 不接管默认短信角色的另一原因：默认角色需承担完整短信 UI/写库/MMS 义务，并会顶掉用户日常使用的小米短信，工程成本与体验损失都不可接受。
- 广播接收器内同样**同步落盘**原始短信（发件人、正文、卡尾号、时间），解析异步。
- 隐私约束不变：原文仅本机加密存储；Logcat、Git、测试报告、远端同步不得含原文（T00 §5 继续有效）。
- 用户拒绝授予短信权限时系统照常运行，覆盖面板标记"短信证据源缺失"（V1 §4.2 末段不变）。

### 3.3 受限无障碍观察器（增强层，不承载完整性）

V1 §4.3 全部条款不变，补充定位声明：

- 无障碍层只负责两件事：付款成功瞬间补全字段（商户、支付方式、卡尾号），以及在用户完成登录/生物识别后辅助读取官方账单页。
- 无障碍识别结果**永不**直接进入正式账，也**永不**作为某周期"无漏账"的证据。
- 页面不可读、结构变化、受保护时记录适配失效事件，禁止伪造成功。

### 3.4 已知实时盲点（必须显式登记，不得隐瞒）

以下场景实时层结构性抓不到或抓不全，只能由对账层兜底：

1. 微信转账给个人、微信红包、部分小程序/商户内支付：可能只有微信应用内"微信支付"服务消息而无系统通知，或通知文案缺金额。本方案不读取聊天页面，此类事件由微信账单导出/账单页巡检（M4 最高优先级导入源）补入。
2. 无通知的后台代扣、自动续费（V1 §10 用例 6 已覆盖）。
3. 锁屏清理/系统杀服务且通知栏条目也被清除的极端叠加场景：补偿扫描失效，仅对账可补。

每类盲点在对账补齐后，补入的账目须标记 `backfilled_from` 来源，用于统计各通道真实漏捕率，指导后续加固。

### 3.5 官方账单导入与巡检

V1 §4.4 不变。补充一条：对账游标按账户持久化（最后已核验交易时间/官方行号/账期），巡检任务以此计算未覆盖时间段并生成 `CoverageGap`，禁止只记"最近同步成功"。

## 4. 写入路径与崩溃安全

统一写入管线（通知、短信、无障碍、账单导入共用）：

```text
系统回调/广播
  → 同步 append-only 写入 raw_observation（WAL 模式，事务内完成，含来源、来源 key、内容哈希、双时间戳、UserHandle）
  → 返回系统（回调总耗时应 < 5ms）
  → 异步工作队列：解析 → 金融来源判定 → 候选生成 → 观察链接
  → 解析失败的观察保持 PENDING_PARSE，可重试，永不静默丢弃
```

数据库级防重（把"不重复"交给约束而非应用逻辑）：

| 表 | 唯一约束 | 冲突行为 |
|---|---|---|
| `raw_observation` | `(source, source_key, content_hash)` | `INSERT OR IGNORE`，冲突时重复计数 +1 |
| `observation_revision` | `(observation_id, revision_hash)` | 忽略重复 |
| `canonical_transaction` | `(strong_id_hash)`（有强标识时） | 冲突即合并证据链接，不新增交易 |
| `ledger_entry` | `(canonical_tx_id, account_id, direction)` | 冲突进入异常，不覆盖 |

强标识只存不可逆摘要 + 必要尾部字符（V1 §5.2 不变）。

## 5. 去重与配对的阶段划分（对 V1 §5 的实现级澄清）

**实时层严禁跨来源合并。** 原因：支付宝/微信系统通知通常不含交易号，银行短信通常只有卡尾号+金额+时间——V1 §5.2 的强标识在实时层几乎不可得。因此：

- 实时层只做：同 key 修订去重、同哈希重复投递计数、候选生成。
- 支付宝通知 + 银行短信 + 微信通知在实时层是**多条独立候选，这是合法且预期的冗余**，不构成"记重复"。
- 跨来源配对（V1 §5.3 集合匹配）统一在对账层执行，仅在"双方权威记录存在 + 金额币种一致 + 卡尾号对应 + 时间商户相容 + 唯一一对一"五条件齐备时合并为一笔 `CanonicalTransaction`；同窗口多候选无法唯一配对时进冲突队列（V1 §5.3、§3.3 不变）。
- "不记重复"的验收对象是正式账，不是候选列表。UI 必须把候选数与正式账数分开显示，避免冗余候选被误读为重复记账。

## 6. 健康监控与 CoverageGap

V1 §7、§8 原则不变，M2 必须落到以下具体机制：

1. `onListenerDisconnected` / 无障碍服务断开 → 立即生成 `CoverageGap`（开始时间）。
2. BootReceiver：开机后校验通知使用权、短信权限、无障碍服务是否仍有效，失效即生成缺口并通知用户。
3. WorkManager 周期健康检查（≥ 每 6 小时一次，HyperOS 上需配合 §2 保活设置）：校验服务存活、最近事件时间、补偿扫描是否执行。
4. 静默死亡检测：HyperOS 可能杀服务后不再回调。以"系统/常用应用通知基线 + 服务存活探测"判定无事件是正常还是断连；无法区分时保守生成缺口。
5. 恢复连接只关闭缺口的结束时间，**不抹掉缺口**；缺口区间内的交易由对账补齐后，缺口标记为 `BACKFILLED`。

## 7. 数据模型修订点（M1 范围）

在 V1 §3.2 实体基础上：

- `Observation` 增加字段：`user_handle`、`post_time`、`received_time`、`capture_path`（`LIVE_CALLBACK` / `RECONNECT_SWEEP` / `SMS_BROADCAST` / `SMS_BACKFILL` / `A11Y` / `BILL_IMPORT`）、`parse_state`。
- `CanonicalTransaction` 增加字段：`backfilled_from`（可空，标记对账补账来源通道）。
- `CoverageGap` 增加字段：`state`（`OPEN` / `BACKFILLED`）、`detector`（产生缺口的检测机制）。
- T03/T04 既有数据迁移保留，不静默清除（V1 §9 M1 不变）；T04 的异步写入路径按 §4 重写。

## 8. 里程碑修订

- M1（完整性数据内核）：新增 §4 写入管线与 §7 字段；新增约束级防重的单元测试与仪器化测试。
- M2（实时传感器）：短信实现改为 §3.2 方案；新增重连补偿扫描、BootReceiver、健康检查、双开支持；支付宝包名修正 `com.eg.android.AlipayGphone`（V1 原定项不变）。**数据库加密（SQLCipher + Android Keystore）必须在短信采集启用前落地**（V1 §8 要求；M1 调试阶段暂存的为通知原文，属过渡态）。
- M3/M4/M5：不变。M4 中微信账单导入为最高优先级（对应 §3.4 盲点 1）。
- 新增 M2 出口标准：在 HyperOS 上连续 72 小时保活，杀进程/重启/断连三种故障注入后补偿机制全部生效。

## 9. 新增硬性测试用例（追加至 V1 §10，编号 13–16）

13. Listener 断连重连后，`getActiveNotifications()` 补偿扫描捞回断连期存活通知，且与已落库事件不产生重复。
14. 回调到达后、异步解析前 `kill -9`：重启后原始观察仍在，解析队列继续，事件不丢。
15. 双开应用通知：按 UserHandle 正确归属，不与主空间混淆，未登记双开实例单独成组。
16. 微信转账（仅应用内消息、无系统通知）：实时层无候选不报错，微信账单导入后正常补账并标记 `backfilled_from`，不进入异常队列。

## 10. 本方案明确不做的事

1. 不使用 Root/Hook/Shizuku 读取任何金融 App 私有数据（§2 理由）。
2. 不申请默认短信角色（§3.2 理由）。
3. 不在实时层做跨来源合并、不以金额+时间做自动去重（V1 §5.1 禁令不变）。
4. 不把无障碍/通知/短信任何单一来源当作完整性证据。
5. 不向 Logcat/Git/测试报告/远端写入任何原文与完整标识（T00 §5 不变）。
6. 不在完整性内核（M1）完成前把 T04 探针当作记账实现（V1 决策 10 不变）。
